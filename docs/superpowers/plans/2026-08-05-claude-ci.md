# Claude-Integrated CI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a lean lint+types CI workflow and three on-demand Claude workflows to the `kumarsaroj18/plane` fork, so arbitrary prompts can be run against the project from GitHub Actions.

**Architecture:** Four independent workflow files, one per trigger. Permissions are scoped per file: deliberate triggers (manual dispatch, `@claude` mention) get `contents: write`; the automatic PR review gets `contents: read` plus a read-only tool allowlist. Prompts live as versioned markdown in `.github/prompts/` and are selected by a dispatch dropdown or overridden by free text.

**Tech Stack:** GitHub Actions, `anthropics/claude-code-action@v1`, pnpm 11 + turbo, Node 22.18.0, oxlint, actionlint.

## Global Constraints

- Branch: `feat/workshop`. Never commit to `preview`.
- Node version is **22.18.0** exactly (from `.mise.toml`). Pin it explicitly in every `setup-node` step.
- Package manager is pnpm via corepack. Always `pnpm install --frozen-lockfile`.
- Pin the action as `anthropics/claude-code-action@v1`.
- Auth is `claude_code_oauth_token: ${{ secrets.CLAUDE_CODE_OAUTH_TOKEN }}`. Never `anthropic_api_key`.
- Every Claude job needs `id-token: write` in addition to its other permissions.
- Every job sets `timeout-minutes` and every workflow sets a `concurrency` group with `cancel-in-progress: true`, **except `claude-mention.yml`**, which deliberately uses `cancel-in-progress: false` — see Task 3 for the rationale. This exception was confirmed with the user during pre-flight review; it is not a task deviating from spec.
- The nine inherited upstream workflows are never modified or deleted.
- Never interpolate `${{ inputs.* }}` directly inside a `run:` block. Bind it to `env:` first — direct interpolation is a script-injection vector.
- **Merge-to-preview policy (established during Task 1):** GitHub only makes a `workflow_dispatch`-triggered workflow runnable once its file exists on the repo's default branch (`preview`), regardless of `--ref`. `pull_request`-triggered workflows are the exception — they run from the PR head branch's own copy, no merge required, confirmed when `ci.yml`'s checks passed on PR #1 before it was merged. `issue_comment`/`issues`-triggered workflows are event types with no branch context of their own, and are very likely subject to the same default-branch requirement as `workflow_dispatch` — treat this as unconfirmed until a task actually verifies it live, not as settled fact. Policy: once a task's PR shows its required checks passing, the implementer merges it directly (`gh pr merge --merge` — a real merge commit, matching PR #1's precedent; never `--squash` or `--rebase`, to keep the commit SHAs already recorded in the ledger valid) before attempting any `workflow_dispatch` or comment-triggered live verification. This was an explicit policy choice by the user: implementers merge automatically, without pausing to ask each time.
- The tool flag inside `claude_args` is `--allowedTools`, camelCase.

## How verification works here

These are YAML workflows, not library code, so the test cycle is not pytest. Each task uses a two-stage loop:

1. **Static:** `actionlint` on the file. Catches YAML errors, bad expressions, invalid `needs`/`if` references, and shellcheck issues inside `run:` blocks.
2. **Live:** trigger the workflow on GitHub and observe the run reach `completed / success` via `gh run watch`.

A task is done only when stage 2 is green. A workflow that lints but has never run is not done.

- [ ] **Step 3: Create `.github/workflows/ci.yml`**

```yaml
name: CI

on:
  pull_request:
    branches: [preview]
    types: [opened, synchronize, reopened, ready_for_review]
  workflow_dispatch:

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

env:
  NODE_VERSION: "22.18.0"

jobs:
  lint:
    name: Lint (oxlint)
    runs-on: ubuntu-latest
    timeout-minutes: 10
    env:
      TURBO_SCM_BASE: ${{ github.event.pull_request.base.sha }}
      TURBO_SCM_HEAD: ${{ github.sha }}
    steps:
      - name: Checkout
        uses: actions/checkout@v6
        with:
          fetch-depth: 50
          filter: blob:none

      - name: Set up Node
        uses: actions/setup-node@v6
        with:
          node-version: ${{ env.NODE_VERSION }}

      - name: Enable pnpm
        run: corepack enable pnpm

      - name: Resolve pnpm store path
        run: echo "STORE_PATH=$(pnpm store path --silent)" >> "$GITHUB_ENV"

      - name: Cache pnpm store
        uses: actions/cache@v5
        with:
          path: ${{ env.STORE_PATH }}
          key: pnpm-store-${{ runner.os }}-${{ hashFiles('**/pnpm-lock.yaml') }}
          restore-keys: |
            pnpm-store-${{ runner.os }}-

      - name: Install dependencies
        run: pnpm install --frozen-lockfile

      # --affected needs a base ref to diff against. On workflow_dispatch there is
      # no pull_request payload, so TURBO_SCM_BASE is empty and we check everything.
      - name: Run oxlint
        run: |
          if [ -n "${TURBO_SCM_BASE}" ]; then
            pnpm turbo run check:lint --affected
          else
            pnpm turbo run check:lint
          fi

  types:
    name: Type check (tsc)
    runs-on: ubuntu-latest
    timeout-minutes: 20
    env:
      TURBO_SCM_BASE: ${{ github.event.pull_request.base.sha }}
      TURBO_SCM_HEAD: ${{ github.sha }}
      NODE_OPTIONS: "--max-old-space-size=4096"
    steps:
      - name: Checkout
        uses: actions/checkout@v6
        with:
          fetch-depth: 50
          filter: blob:none

      - name: Set up Node
        uses: actions/setup-node@v6
        with:
          node-version: ${{ env.NODE_VERSION }}

      - name: Enable pnpm
        run: corepack enable pnpm

      - name: Resolve pnpm store path
        run: echo "STORE_PATH=$(pnpm store path --silent)" >> "$GITHUB_ENV"

      - name: Cache pnpm store
        uses: actions/cache@v5
        with:
          path: ${{ env.STORE_PATH }}
          key: pnpm-store-${{ runner.os }}-${{ hashFiles('**/pnpm-lock.yaml') }}
          restore-keys: |
            pnpm-store-${{ runner.os }}-

      # check:types declares dependsOn ["^build"] in turbo.json, so turbo builds
      # dependency packages itself. Caching .turbo is what makes that affordable.
      - name: Cache turbo
        uses: actions/cache@v5
        with:
          path: .turbo
          key: turbo-${{ runner.os }}-${{ github.sha }}
          restore-keys: |
            turbo-${{ runner.os }}-

      - name: Install dependencies
        run: pnpm install --frozen-lockfile

      - name: Run tsc
        run: |
          if [ -n "${TURBO_SCM_BASE}" ]; then
            pnpm turbo run check:types --affected
          else
            pnpm turbo run check:types
          fi
```

`.github/prompts/idor-tenant-isolation.md`:

```markdown
Audit for insecure direct object reference (IDOR) and multi-tenancy isolation
failures — cases where one authenticated user can act on another user's or
another workspace's data by supplying a different ID in the request.

This is a multi-tenant Django REST Framework API under `apps/api/plane`. The
core scoping hierarchy is Workspace -> Project -> Issue (and related models).
Permission classes live under `apps/api/plane/app/permissions` and
`apps/api/plane/utils/permissions`; endpoint scoping happens both through URL
path segments (workspace slug, project ID) and through request payload fields.

For every view under `apps/api/plane/app/views` and `apps/api/plane/space/views`
that accepts an ID in the URL, query string, or request body (workspace ID,
project ID, issue ID, member ID, or similar), check:

1. Does `get_queryset()` filter by the workspace/project the authenticated user
   actually belongs to, or does it trust an ID from the request unfiltered?
2. Can a payload field (not the URL) override which workspace or project a write
   applies to, bypassing the permission class that gated the URL-level object?
3. Do nested resources (e.g. an issue comment, an issue activity) re-verify
   workspace/project membership, or only check that the parent issue exists?
4. Are `pk`/`id` lookups scoped with `.filter(workspace=..., project=...)` before
   `.get()`, or does an unscoped `Model.objects.get(pk=...)` let a valid ID from
   any tenant resolve?

For each finding, give the file path, line number, the exact request a malicious
authenticated user (member of a different workspace) could send, and what they
would gain access to. Do not report a finding where the permission class already
enforces workspace membership at the queryset level — verify by reading the
permission class, not just the view.
```

`.github/prompts/n-plus-one-queries.md`:

```markdown
Find N+1 query problems in the Django backend under `apps/api/plane`.

Look at views, serializers, and viewsets — particularly list endpoints in
`apps/api/plane/app/views` that serialize collections (issues, projects, workspace
members, comments). For each serializer field that traverses a foreign key,
many-to-many, or reverse relation:

1. Does the queryset use `select_related` for each forward foreign key the
   serializer touches, and `prefetch_related` for each reverse relation or
   many-to-many?
2. Does a serializer method field (`SerializerMethodField`) run a query per
   object rather than using an annotated or prefetched value?
3. Are there loops in view code that call `.save()`, `.get()`, or iterate a
   related manager once per item in an outer queryset?
4. Do paginated list views apply the same optimizations as their unpaginated
   counterparts, or did an optimization get missed on one but not the other?

For each finding, give the file path, line number, the query count you'd expect
under load (e.g. "1 + N where N is the number of issues returned"), and the
concrete `select_related`/`prefetch_related`/annotation fix. Prefer findings you
can support by reading the serializer's declared fields against the view's
`get_queryset()` — don't speculate about code you have not read.
```

```yaml
        with:
          fetch-depth: 0

      # Inputs are bound to env rather than interpolated into the script body.
      # Interpolating ${{ inputs.prompt }} directly into run: would let prompt
      # text terminate the shell command and execute arbitrary code.
      - name: Resolve prompt
        id: resolve
        env:
          FREE_TEXT: ${{ inputs.prompt }}
          PROMPT_FILE: ${{ inputs.prompt_file }}
          SCOPE: ${{ inputs.scope }}
        run: |
          set -euo pipefail

          if [ -n "${FREE_TEXT}" ]; then
            SOURCE="free-text"
            BODY="${FREE_TEXT}"
          else
            SOURCE=".github/prompts/${PROMPT_FILE}"
            if [ ! -f "${SOURCE}" ]; then
              echo "::error::Prompt file not found: ${SOURCE}"
              exit 1
            fi
            BODY="$(cat "${SOURCE}")"
          fi

          echo "Prompt source: ${SOURCE}"

          {
            echo "body<<CLAUDE_PROMPT_EOF"
            echo "REPO: ${GITHUB_REPOSITORY}"
            echo "BRANCH: ${GITHUB_REF_NAME}"
            if [ -n "${SCOPE}" ]; then
              echo "SCOPE: restrict your analysis to the path '${SCOPE}'"
            fi
            echo ""
            echo "${BODY}"
            echo "CLAUDE_PROMPT_EOF"
          } >> "${GITHUB_OUTPUT}"

      - name: Run Claude
        uses: anthropics/claude-code-action@v1
        with:
          claude_code_oauth_token: ${{ secrets.CLAUDE_CODE_OAUTH_TOKEN }}
          prompt: ${{ steps.resolve.outputs.body }}
          claude_args: --model ${{ inputs.model }} --max-turns 30
```

```yaml
name: Claude — automatic PR review

on:
  pull_request:
    types: [opened, synchronize, reopened, ready_for_review]

concurrency:
  group: ${{ github.workflow }}-${{ github.event.pull_request.number }}
  cancel-in-progress: true

jobs:
  review:
    name: Review pull request
    runs-on: ubuntu-latest
    timeout-minutes: 20
    if: github.event.pull_request.draft == false
    # No contents: write. This workflow fires automatically, including on commits
    # Claude itself just pushed via the dispatch workflow. Comment-only is enforced
    # twice: here, and again by the --allowedTools list below.
    permissions:
      contents: read
      pull-requests: write
      id-token: write
    steps:
      - name: Checkout
        uses: actions/checkout@v6
        with:
          fetch-depth: 1

      - name: Review
        uses: anthropics/claude-code-action@v1
        with:
          claude_code_oauth_token: ${{ secrets.CLAUDE_CODE_OAUTH_TOKEN }}
          track_progress: true
          use_sticky_comment: true
          prompt: |
            REPO: ${{ github.repository }}
            PR NUMBER: ${{ github.event.pull_request.number }}

            Review this pull request against the conventions in AGENTS.md:
            camelCase for variables and functions, PascalCase for components and
            types, strict TypeScript, oxlint via .oxlintrc.json, oxfmt formatting,
            MobX stores in packages/shared-state.

            Focus on, in order:

            1. Correctness — logic errors, unhandled edge cases, wrong async handling.
            2. Security — injection, auth gaps, unsafe rendering of user input.
            3. Error handling — try/catch with proper error types.
            4. Consistency — divergence from patterns in the surrounding package.

            Use inline comments for specific line-level issues. Use one top-level
            comment for general observations.

            Be concise and concrete. If the diff is small and clean, say so in one
            or two sentences rather than manufacturing feedback.
          claude_args: |
            --allowedTools "mcp__github_inline_comment__create_inline_comment,Bash(gh pr comment:*),Bash(gh pr diff:*),Bash(gh pr view:*),Read,Grep,Glob"
```

# Workflows

This fork adds four workflows alongside the nine inherited from `makeplane/plane`.
The inherited files are untouched; anything below is fork-local.

## Added by this fork

| File | Trigger | Claude can write? |
|---|---|---|
| `ci.yml` | PR into `preview`, or manual dispatch | n/a |

| `claude-mention.yml` | `@claude` in a comment or issue | Yes |
| `claude-review.yml` | Every non-draft PR | No, comment-only |

Permissions are scoped by how deliberate the trigger is. Dispatch and mention are
explicit human actions, so they get `contents: write`. The automatic PR review does
not, because it fires unattended — including on commits Claude itself just pushed.

## Running a prompt

From the Actions tab, choose **Claude — manual prompt runner**, then **Run workflow**.

- **prompt_file** — pick a saved prompt from `.github/prompts/`.
- **prompt** — free text. When non-empty this wins and `prompt_file` is ignored.
- **model** — `sonnet` (default), `opus`, or `haiku`.
- **scope** — optional path such as `apps/web` to narrow the analysis.

From the CLI:

```bash
gh workflow run claude-dispatch.yml --ref feat/workshop \
  -f prompt_file=idor-tenant-isolation.md \
  -f model=sonnet \
  -f scope=apps/api
```

| File | Purpose |
|---|---|
| `test-coverage-gaps.md` | Highest-risk missing tests (default) |
| `security-audit.md` | Injection, auth, secrets, unsafe rendering |
| `idor-tenant-isolation.md` | Cross-tenant/IDOR access checks |
| `n-plus-one-queries.md` | N+1 query detection in the Django ORM layer |
| `secret-scan.md` | Committed secrets and credentials |

| `dead-code.md` | Unused functions, components, and exports |
| `api-versioning.md` | API versioning strategy assessment |

| `dependency-audit.md` | Catalog bypasses, version skew, phantom deps |

Adding a prompt takes two edits: create the file in `.github/prompts/`, then add its

GitHub Actions `choice` inputs are static and cannot enumerate a directory, so the
dropdown must be maintained by hand. The file is the source of truth; the dropdown is
only a menu.

## Auth

All Claude workflows authenticate with the `CLAUDE_CODE_OAUTH_TOKEN` repo secret,
which is generated by `claude setup-token` and backed by a Claude subscription rather
than per-token API billing. Rotate it with:

```bash
claude setup-token
gh secret set CLAUDE_CODE_OAUTH_TOKEN
```

## Known limits

- Pull requests opened from a different fork do not receive repository secrets, so
  `claude-review.yml` will not run Claude on them.
- `ci.yml` uses `turbo --affected`, which needs a PR base to diff against. On manual
  dispatch there is no base, so it checks the entire monorepo and takes far longer.
- There is no scheduled workflow. Claude runs only when explicitly invoked.
- `workflow_dispatch` workflows (`claude-dispatch.yml`) only become runnable once
  their file exists on the repo's default branch (`preview`) — GitHub does not
  discover a dispatchable workflow off a feature branch, regardless of `--ref`.
  `pull_request`-triggered workflows (`ci.yml`, `claude-review.yml`) don't have this
  restriction; they run from the PR's own branch.
